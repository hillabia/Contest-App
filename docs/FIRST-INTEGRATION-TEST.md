# Contest-App — first integration test (development only)

## Prerequisites

- The database project is **contest-app-dev**. The three round lifecycle migrations are registered and applied.
- The private `contest-photos` bucket must exist (max file size 5 MB).
- Create a dedicated administrator using Supabase Authentication > Users. Do not store passwords or tokens in the repository.
- Copy `.env.example` to `.env.local`. Set the server variables, `CONTEST_ADMIN_USER_ID` to the administrator's Auth UUID, and the public URL + publishable/anon key. Never prefix a service-role key with `NEXT_PUBLIC_`.
- Use a *development deployment only*, not the production environment.

## Controlled test

1. Log in at `/admin` as the dedicated administrator; check that an unrelated account cannot call admin APIs.
2. Create a contest with a future registration closing time and later voting closing time.
3. Register at least three sample participants through `/participar`; verify private image storage and one-time access codes. Use nonpersonal test photos and names.
4. After the registration deadline, start the regular round from `/admin`, then use separate participant codes to vote on all eligible photos in `/votar`.
5. Confirm a code cannot vote twice, cannot vote for its own photo and cannot vote after the deadline.
6. Close the round only after the voting deadline. Examine private results, trigger tie-breaks if applicable, and verify public scores remain hidden until reveal.
7. Finalize and reveal only with all rounds closed and all podium ties resolved. Verify `/podio` shows only permitted data.
8. Do **not** leave personal data behind. Automated full deletion is still unimplemented: this blocks real-user pilots. Plan a controlled manual cleanup of synthetic test data with explicit review.

## Do not yet mark production-ready

- SQL/schema migrations have been applied, but end-to-end verification of voting, ties and reveal is still pending.
- The application has no confirmed tested purge workflow or rate-limiting policy.
- The migration history generated by Supabase uses different versions from the repository filenames; reconcile before automated migration deployment.
- CI success is not a substitute for the above functional checks.
